You are reviewing Android manifest and network security config files for three security flags that each introduce distinct risks.

## 1. android:debuggable="true"

```xml
<application android:debuggable="true" ...>
```

When an app is marked debuggable, any app on the device (or an attacker with USB access) can:
- Attach a debugger via `adb` and step through code, inspect memory, and extract secrets
- Call `am start` with arbitrary intents to force the app into debug mode
- Dump the app's memory including encryption keys, session tokens, and cleartext passwords

**This flag must be `false` or absent in production builds.** Debug builds generated by Android Studio automatically set this; the problem is when it leaks into release builds, often via misconfigured Gradle scripts or CI pipelines that don't use the release build type.

**Cross-file check:** Look for `buildTypes { release { debuggable true } }` in `build.gradle` — that's where this gets set incorrectly for release builds.

## 2. android:allowBackup="true"

```xml
<application android:allowBackup="true" ...>
```

When backup is enabled, `adb backup` (or Android's cloud backup system) can extract:
- The app's entire private data directory (`/data/data/com.package/`)
- Databases including plaintext or encrypted credentials
- SharedPreferences containing tokens and session data

An attacker with physical access to the device (or a malicious app with `BACKUP` permission on older Android versions) can restore this backup to another device, effectively cloning the victim's session.

**Note:** Since Android 12, the default changed to `false`. Apps targeting API 31+ that don't declare `allowBackup` are safe. Apps targeting lower APIs default to `true`.

**Context matters:** Some apps intentionally allow backup for user convenience. The risk is low if the app uses encrypted shared preferences and encrypted databases. Check what sensitive data the app stores.

## 3. User certificate trust (`<certificates src="user">`)

In `network_security_config.xml`:
```xml
<network-security-config>
  <base-config>
    <trust-anchors>
      <certificates src="system"/>
      <certificates src="user"/>  <!-- VULNERABLE -->
    </trust-anchors>
  </base-config>
</network-security-config>
```

Trusting user-installed certificates allows MITM attacks: an attacker who tricks the user into installing their CA certificate can intercept all of the app's HTTPS traffic, including API calls, authentication tokens, and sensitive data.

This is commonly added during development to allow proxy tools like Burp Suite — the vulnerability is when it is left in production builds.

## True positive criteria

| Flag | Flag when |
|---|---|
| debuggable="true" | Present in any manifest that could reach a production build |
| allowBackup="true" | App stores sensitive data in unencrypted SharedPreferences or database |
| user cert trust | Present in a network security config that applies to production endpoints |

## What to ignore

- `debuggable="true"` in manifests clearly scoped to debug build variants only (`src/debug/AndroidManifest.xml`)
- `allowBackup="true"` when the app demonstrably stores no sensitive data locally (e.g., stateless utilities)
- User cert trust in a `<debug-overrides>` block — Android only applies these in debug builds

## Examples

True positives:
```xml
<!-- Main AndroidManifest.xml — applies to all builds -->
<application
    android:allowBackup="true"
    android:debuggable="true"
    android:label="@string/app_name">
```
```xml
<!-- network_security_config.xml in src/main/ — applies to release -->
<base-config cleartextTrafficPermitted="false">
  <trust-anchors>
    <certificates src="system"/>
    <certificates src="user"/>
  </trust-anchors>
</base-config>
```

False positives to skip:
```xml
<!-- src/debug/AndroidManifest.xml — only affects debug builds -->
<application android:debuggable="true">
```
```xml
<!-- network_security_config.xml with debug-overrides only -->
<debug-overrides>
  <trust-anchors>
    <certificates src="user"/>
  </trust-anchors>
</debug-overrides>
```

Report which flags are set, which build variants they affect (check if the manifest is in `src/main/`, `src/debug/`, or `src/release/`), and what sensitive data the app stores that would be exposed.
